# 初回版の範囲と記録方針
Updated: 2026-11-06 JST

関連：[ロードマップ](ROADMAP.md)、[利用フロー](WORKFLOW.md)、[デザイン方針](DESIGN.md)

## 初回の成果物
翌週の献立を組むと、期限内の冷凍料理で足りる分、追加で作る料理、必要な食材、まとめられる調理工程がつながり、実際の作成・使用後の在庫が更新される。
主利用者がスマホで使える家庭用アプリ。NAS上で実行/永続保存を優先。家内/家外の利用、新たな月額課金回避は維持する。

## 普段行うこと
1. 週の献立：朝/昼/夜へ登録済み料理と必要量を置く。食事時に用意する食品も含める。同じ内容の複製と一部変更ができる。
2. 買い物/作るもの：現物在庫で賄える分を控除し、不足をまとめる。献立を変えると再計算する。
3. 調理完了：予定から料理名等を引き継ぎ、実際にできた数量、作成/冷凍日、期限を確認してまとめて登録する。
4. 食事準備：必要品と使用量を確認してまとめて使用を確定する。変更があればその品だけ直す。
5. 訂正/廃棄：履歴から修正し、現物との差を直せる。実際の物の状態と、記録の誤りの訂正を区別する。

## 入力負担の設計目標（検証前の目標）
- 定型の一食は、使用品が合っていれば食事単位の一度の確定で記録できること。
- 料理名・レシピ・通常の一回量を日々入力し直さないこと。
- 週末は料理一覧で実出来高等を一括確認でき、容器一個ずつの登録を必須にしないこと。
- 通常操作と訂正を分けるが、訂正を隠れた複雑な管理画面へ追いやらないこと。
- 主利用者が続けたいと判断することが必須。現在の所要時間や達成率は未測定。現時点で「記録時間を短縮した」と主張しない。

## 数量と期限の扱い
| 対象 | 初回の方針 | 未確認を扱う方法 |
| --- | --- | --- |
| 食材 | レシピの必要量と、把握できる手持ち量を比較。重さ/個数等の単位と正味/購入時の状態を区別 | 数量や換算不明は「手持ち未確認」「換算未確認」。ゼロ在庫や1対1換算に置換しない。購入量を確定できる範囲を明示 |
| 冷凍料理 | 作成ごとのロット、数量と単位を管理 | 一容器=一食分と固定しない。料理ごとの一回量や換算は確認/設定できる形を要求。未設定なら不明表示 |
| 予定 | 使用可能な冷凍在庫の予約と不足計算 | 予約時点では実在庫を消費しない。同じ在庫の重複予約を防ぐ |
| 期限 | 使用予定日と照合し、期限を超える分は使える在庫に含めない | 本/ラベル/確認された家庭方針等に基づく期限を扱う。未設定ロットは「期限未確認」とし使用可能と断定しない。独断の保存日数を標準値として埋めない |
| 出来高 | 実際にできた分だけ完成品在庫を増やす | 本の予定量を実測値と偽らない。予定と違う場合に今後の不足を更新 |
| 共通工程 | 同日内の産出/配分として重複を防ぐ | 中間素材在庫を標準操作へ再導入しない。未確認の任意倍率で工程を安全に増量できると仮定しない |

この方針は未知の実値を作り込まず扱うための仕様。実際に使う数量換算・期限根拠を確認するタスクを完了扱いにするものではない。

## 初期コンテンツと検証
提供資料の代表週を計算/登録構造の検証用に優先する。子どもへその献立を推奨したり、家庭の採用メニューを決定したりしたものではない。
料理本体、共通工程、必要量/配分、食数/個数、食事時追加食品、出典、未確認参照を分ける。初期データに確認が必要な値を明示し、後から変更しても過去の記録が変わらないようにする。
一週間の基本フローに加え、献立差替え、出来高不足、期限を超える予約、二重操作、使用記録の訂正を検証対象とする。
検証用の例データと家庭の実在庫は分離する。

## 最初に増やさないもの
自動で栄養や食事の適否を判断する機能、無限のレシピ提案、常時AIチャット、素材ごとの在庫、一般公開を初回必須にはしない。端末への通知配信方式は未選定であり、初回はアプリ内で不足/期限の確認を成立させる。
可愛らしさはDESIGN.mdを適用する。実用の数量・期限・保存状態の読みにくさで演出を優先しない。

## ローンチへ持ち越せない未確認
数量換算と食材記録粒度の家庭への適合、期限条件、採用する初期メニュー、実端末の操作負担、NASでの実行・家外接続・認証・保存・バックアップ復元・更新後保持。
これらはROADMAP.mdで未完了として残す。設定可能な構造を提案したことは、値や利用実績の検証完了ではない。
